## 1. Documentation system and build

### What is strong

**Single source tree, correctly bounded.** All documentation source is under `docs/` with one `conf.py`. Build outputs and the four generated page families are git-ignored (`.gitignore`: `docs/_build/`, `docs/api_reference.rst`, `docs/api_opus_*.rst`, `docs/api_guide_fields_table.rst`), and `git status` confirmed clean after three separate builds.

**`conf.py` meets every requirement of `doc_python.mdc` §3 and then exceeds it.** Every mandated extension is enabled (`docs/conf.py:77-86`): autodoc, napoleon, viewcode, intersphinx, `myst_parser`, `sphinxcontrib.mermaid`, plus the two local generators. `source_suffix` covers `.rst` and `.md` (`:88-91`). Napoleon is configured for Google style with `napoleon_use_param` and `napoleon_use_rtype` (`:132-140`). The version comes from `importlib.metadata.version('rms-opus')` (`:72`), not a literal. Both `src/` and `_ext/` go on `sys.path` (`:33-34`) so autodoc needs no install step.

Two pieces of `conf.py` are better than the rule asks for and deserve saying so:

- **`REFERENCE_ALIASES` and the `missing-reference` handler** (`docs/conf.py:162-213`). Rather than silencing names that no inventory carries under autodoc's spelling, the handler *rewrites the target so it resolves*, at priority 400 so intersphinx sees the rewrite. Twelve names that would otherwise have become `nitpick_ignore` entries are links instead. The rationale is written down at `:158-161`.
- **`_django_settings.LOGGING_CONFIG = None`** (`docs/conf.py:63`), with the reason at `:56-62`: Django's `dictConfig` sets `disable_existing_loggers`, which would disable the loggers Sphinx created before importing `conf.py` — the build would then report no warnings at all and `-W` could never fail. That is a subtle way for a documentation gate to become silently vacuous, and it was found and neutralized.

**`nitpick_ignore` is exemplary.** Exactly five entries (`docs/conf.py:221-235`), each carrying a comment saying why it cannot be linked: two third-party packages that publish no Sphinx inventory (`pdslogger.PdsLogger`, `requests.RequestException`), a type alias declared inside `if TYPE_CHECKING:` that autodoc therefore never sees, and a `TypeVar`. `nitpick_ignore_regex` is empty (`:237`). No entry silences a symbol the project owns — precisely what `doc_python.mdc` §3's last bullet forbids. One suppression exists, `suppress_warnings = ['myst.header']` (`:111`), and it too carries its reason.

### Findings

**F1.1 — Medium. The justification for the one suppressed warning class is wrong about half the files it names.**
`docs/conf.py:105-111` explains `suppress_warnings = ['myst.header']` as: *"The README and CONTRIBUTING are included from partway down, after the badge block, so the fragment MyST sees starts at the first section rather than at the title."* That is true of the README — `docs/index.rst:6` uses `:start-after: <!-- start-after-point -->`. It is false of `CONTRIBUTING.md`: `docs/dev_guide_contributing.rst:9-10` includes the whole file from its `#` title with no `:start-after:` option at all. The suppression may still be needed for the README alone, but the recorded reason misdescribes the build.

**F1.2 — Low. `intersphinx_mapping` omits a declared runtime dependency.**
`docs/conf.py:144-150` maps only `python` and `django`. numpy is a hard `[project]` dependency (`pyproject.toml:16`, `numpy>=1.26`) and four numpy types are named in docstrings that reach the API reference — `numpy.int64`, `numpy.float64`, `numpy.integer`, `numpy.str_` (e.g. in `src/opus_import/obs/field_types.py`). numpy publishes an inventory. `doc_python.mdc` §3 asks intersphinx to cover "Python and key third-party dependencies". Small, because numpy appears in only 5 files under `src/` and mostly outside annotations.

**F1.3 — Medium. Time-anchored and migration framing, in the API guide and in docstrings.**
`doc_python.mdc` §2 is explicit: *"Never anchor prose to a moment in time or to migration history: avoid 'new', 'legacy', 'old', 'now', 'recently', 'as before', 'backwards compatible'."* The repository observes this rule remarkably well overall — a sweep of `docs/*.rst` for `legacy|deprecated|backwards compatible|as before|recently|formerly|no longer|used to be` returns only four hits, two of which are legitimate (MySQL's own deprecation of a syntax, and a forward-looking dependency exit condition). The genuine violations cluster in one file and a few docstrings:

- `docs/api_guide_calls.rst:17` — *"This data is usually provided for backwards compatibility with legacy applications and should not be relied on for new development."* Three forbidden framings in one sentence.
- `docs/api_guide_calls.rst:33` — *"A few server-side failures also answer 404 rather than 500, for historical reasons."*
- `docs/api_guide_calls.rst:36` — *"Requests that supply a bad field, value, unit, or query type answer with 400 rather than the 404 that earlier versions of OPUS returned for every kind of error. Client code that treats 404 as 'my request was wrong' should be updated to look at 400 for that."* This is the clearest violation in the set.
- `src/opus_log_analyzer/log_analyzer.py:8` (module docstring, rendered into the API reference) — *"`--batch` and `--cronjob` are the modes that run today."*
- `docs/dev_guide_log_analyzer.rst:78` — *"this method is part of the contract but is not reachable today."*
- `src/opus_import/obs/field_types.py:116` — *"so both are None in every row this pipeline writes today."*
- `src/opus_app/settings.py:134` — *"nothing in the web application reads or writes one through the ORM today."*
- `docs/dev_guide_import_fixture.rst:113,117` — *"of which there are none today"*, *"No table is excused today."*
- `src/opus_app/apps/results/views.py:1948` — *"that used to be supplied by the metadata API."*

A note on judgment: the API guide's content here is genuinely useful to a client author, and the repository holds a documented waiver for public web API *behavior* (`docs/dev_guide_conventions.rst:74-79`). That waiver covers behavior, not prose, and `doc_python.mdc` §2 admits no exception. The fix is to restate the same facts as the current contract — "a bad field, value, unit or query type answers 400; a URL naming something that does not exist answers 404" — which loses nothing a caller needs and drops the migration frame. The `today`s are pure noise and cost nothing to delete.

**F1.4 — Low. Unicode em-dashes inside a `.py` file.**

Format conformance is likewise near-total: **zero** `Args:` sections anywhere in `src/`, `docs/_ext/` or `manage.py`, against 476 `Parameters:`, 443 `Returns:`, 162 `Raises:`, 12 `Attributes:` and 9 `Yields:`. Quality at its best genuinely meets `doc_python.mdc` §4's "sufficient to write a black-box test" bar, and does so by documenting edge cases rather than prose-padding:

- `src/opus_support/units.py:615` `convert_to_default_unit` — the strongest in the tree; `Raises:` enumerates each distinct `KeyError` cause and the `ValueError` overflow case, so every branch is testable from the text alone.

Thus methods have to assume that the metadata has changed between calls and they can't cache results."*
- `src/opus_support/sclk.py:183` `parse_galileo_sclk` — gives the exact numeric bounds of every field.

**The API reference generator is the single best piece of documentation engineering in the repository.** `docs/_ext/opus_api_reference.py` walks each package with `pkgutil.walk_packages` and writes one page per package and subpackage before every build, so a module added to `src/` appears in the reference with nothing listed by hand. `_automodule` (`:144-153`) emits `:members:`, `:undoc-members:` and `:show-inheritance:` — exactly the three options `doc_dev_guide.mdc` §6 requires. Two details go beyond the rule:

- `walk_package` passes `onerror=reraise` (`:105-116`) with the reason documented at `:96-102`: without it, `pkgutil` swallows an `ImportError` and a broken subpackage would vanish from the reference *silently*, emitting no warning for `-W` to promote. A broken package now fails the build instead.
- The two excluded modules (`:68-76`) are excluded for stated reasons, and those reasons are *rendered onto the reference's landing page* (`render_index_page`, `:239-251`) rather than being hidden in the generator — because, as the comment says, "a reader who cannot find a module needs to be told it was left out". `absent_phrase()` (`:193-208`) derives the count from the dictionary so the page cannot disagree with the generator.

### Findings

**F2.1 — High. 1,186 undocumented public methods, all of them published.**
Every one is a `field_*` obs-field extractor in `src/opus_import/obs/` (48 files). Of 1,189 such methods repo-wide, 3 carry a docstring. Worst files: `obs_ring_geometry.py` (85), `obs_volume_cocirs_01xxx.py` (78), `obs_surface_geometry_target.py` (62), `obs_volume_ebrocc_xxxx.py` (50).

This is not private. The generator emits `:undoc-members:` (`docs/_ext/opus_api_reference.py:147`) and `EXCLUDED_MODULES` (`:68-76`) excludes only two `opus_app` modules — no `opus_import.obs` module is excluded. Verified in the rendered HTML: **1,185 `field_obs_*` entries appear on `api_opus_import.obs.html`**, each as a bare signature plus a return type and no description whatever, e.g.:

```
field_obs_ring_geometry_ring_radius1()  [source]
    Return type: float | None
```

That page is **1.5 MB**, three times the size of the general index and by far the largest artifact the build produces. This is exactly the case `doc_python.mdc` §4's closing bullet names: *"a missing or thin docstring is a hole in the published API documentation, not a private matter."*

In fairness, this is a **deliberate, written-down policy, not neglect.** `docs/dev_guide_conventions.rst:88-93` states it plainly: *"There is one standing exemption, and it is deliberate: the `field_obs_*` methods of the obs hierarchy do not carry individual docstrings… The authoritative statement of what one of those methods returns is its schema column plus the test that checks the correspondence, which is checkable, where a thousand near-identical hand-written sentences would be a thousand chances to be wrong."* Each class documents the convention collectively (e.g. `src/opus_import/obs/obs_ring_geometry.py:29`). The reasoning is sound and I would not argue for a thousand hand-written sentences either.

But the rule as written admits no exemption, and — more importantly — the *published artifact* is bad regardless of the reasoning: a reader of the API reference gets 1,185 undescribed entries and no on-page explanation of why. Three ways to close it, in increasing order of effort:
1. Add `opus_import.obs.*` to `EXCLUDED_MODULES` with the existing rationale as its reason, so the exclusion is stated on the landing page where a reader will see it. Cheapest, and consistent with how the other two exclusions are handled.
2. Drop `:undoc-members:` for the `obs` pages only, so documented members still appear and the 1,186 do not.
3. Have the generator synthesize a one-line description per `field_*` method from the schema column it fills — turning the checkable source of truth into the published text.

`doc_python.mdc` §4 requires `Parameters:` and, where applicable, `Returns:`/`Raises:`. Measured against real signatures:

## 3. Cross-reference completeness

### What is strong

**Everything that is roled, resolves.** The nitpicky build reports zero unresolved references, so no `:class:`/`:meth:`/`:func:`/`:doc:` target anywhere in the tree is stale. Measured across the 39 narrative files: **272 `:ref:` uses across 77 distinct targets, all resolving** against the 200 explicit `.. _label:` definitions in `docs/` (plus the three Sphinx built-ins `genindex`, `modindex`, `search`) — no orphans, no dangling labels. **39 `:doc:` uses across 15 distinct targets, every target existing.** `docs/dev_guide_architecture.rst:124-147` is representative of the house style at its best: three paragraphs naming eight code objects, every one roled with a `~` prefix. Every chapter ends with an API-reference pointer, per `doc_dev_guide.mdc` §4. The class-diagram blocks correctly carry no cross-references inside them, per §3.

**Bare CamelCase in prose: zero violations.** All 304 occurrences of a known class name outside backticks land in a Mermaid diagram, a code-block body, or a section title — every one exempt under §5's exclusion list. The only bare CamelCase in running prose is proper nouns (MySQL, PyPI, JavaScript, GitHub, NumPy, PyPA, CoreUI, InSb) and two third-party names with no inventory to link to: `PdsViewSet` (`docs/dev_guide_database.rst:129`) and `PdsFile` (`docs/dev_guide_opus_id.rst:440`). `:doc:` targets are all bare page names — relative, no leading `/`, no `../`. ### Findings

**F3.1 — High. Docstrings mark up code objects with single backticks, which are neither cross-references nor literals — and the nitpicky gate is structurally blind to it.**

`docs/conf.py` does not set `default_role`. Sphinx's default is therefore `title_reference`, which renders single-backtick text as *italics* and links nowhere. The docstrings across `src/` use single backticks as their standard markup for code objects. Two measurements:

- Sphinx roles actually used in all of `src/`: **4** (2 `:func:`, 1 `:meth:`, 1 `:class:`).
- Single-backtick spans that a `py:obj` default role cannot resolve: **418**, covering **269 distinct targets**. Measured by rebuilding with `-D default_role=py:obj` (a command-line override; no file was modified).

Every one of the 418 comes from `src/`. **Not one comes from any `.rst` file** — the boundary is exactly the docstring boundary.

The 269 targets split into two populations, and `doc_python.mdc` §5 is violated by both:

*Genuine API symbols written without a role* (at least 46 distinct), which should be `:class:`/`:meth:`/`:func:`/`:mod:` and would then link into the API reference — among them `ObsBase._create_mult`, `ObsBase.convert_filespec_from_lbl`, `Configuration.create_session_info`, `ImportDBSuper`, `LogParser`, `LogReader`, `HtmlGenerator`, `AbstractConfiguration`, `BundleInfo`, `Lexer.tokenize`, `opus_config.get_config`, `opus_app.settings.API_GUIDE_URL`, `numpy.int64`.

*Non-API tokens in single backticks* — file paths (`cart/urls.py`), environment variables (`OPUS_CONFIG`), YAML files (`faq.yaml`), CLI tokens (`django-admin`), URL patterns (`__cart/*`), database columns (`cart`, `recycled`), format names (`pdf`). §5's second bullet is explicit that these belong in *double*-backtick inline literals; in single backticks they render as italic prose and do not even look like code.

Why this matters more than a formatting nit: `-n` cannot catch it. Nitpicky flags cross-references that fail to resolve, and a `title_reference` is not a cross-reference — so the build passing clean provides no assurance at all about these 418 spans, and a symbol renamed tomorrow would leave every one of them silently stale. All four gates described in the build-health table share this blind spot.

The fix is one line plus follow-up work: setting `default_role = 'py:obj'` (or `'any'`) in `conf.py` converts every correctly-written single-backtick symbol into a real link *and* brings all 418 under the nitpicky gate, at which point the build will fail and name each one that needs either a role change or a promotion to double backticks. That is the point — the failures are the inventory.

**F3.2 — Medium. 21 API symbols that do have a reference target are written as inline literals in prose instead of being linked.**

`doc_python.mdc` §5 is explicit that this counts even inside inline literals: *"Bare CamelCase or `module.symbol` text in prose is a violation, even when wrapped in inline literals. Inline literals are for YAML/JSON keys, file paths, CLI tokens, environment variables, and shell snippets — not for API symbols."* Measured over the 8,069 prose lines of the 39 narrative files (block, literal, diagram, comment and title lines excluded), against an AST-built symbol set of 352 classes, 299 module-level functions and 1,686 methods, then filtered to those that actually have an autodoc target in the built reference:

| Kind | Count | Instances |
| --- | --- | --- |
| Public functions and methods needing `:func:`/`:meth:` | **19** | ``get_range_query`` (`dev_guide_database.rst:51`), ``get_longitude_query`` (`:62`), ``get_search_results_chunk`` (`:640`), ``log_error`` (`dev_guide_import_db.rst:365`), ``do_param_info`` (`dev_guide_import_fixture.rst:156`), ``main`` (`dev_guide_environment.rst:132`, `dev_guide_log_analyzer.rst:13,16`, `dev_guide_import_running.rst:451`), ``create_session_info`` (`dev_guide_log_analyzer.rst:105`), ``parse_log_entry`` (`:106`), ``safe_format`` (`:117`), ``get_icon_flags()`` (`:97`), ``compute_longitude_field()`` and ``compute_d_longitude_field()`` (`dev_guide_import_obs.rst:444`), ``opus_support`` (`dev_guide_testing.rst:82`) and ``opus_import`` (`dev_guide_environment.rst:246`) as modules |

**F3.3 — Medium. A further 142 prose mentions name symbols the API reference gives no target to, so §5 cannot be satisfied by editing the prose. This one needs a decision.**

This is the more interesting half, and it exonerates the authors: where a target exists they generally role it, and where none exists they fall back to an inline literal. The literal is the *only* option — adding a role to any of these would fail the `-n` build. Four populations:

**78 mentions of module-level constants** (45 distinct, 17 files) — ``BUNDLE_INFO`` (`dev_guide_import.rst:184,190,450`; `dev_guide_import_config.rst:145,188`; `dev_guide_import_steps.rst:131,388`; `dev_guide_import_obs_classes.rst:11`), ``TABLES_TO_POPULATE``, ``PLANET_GROUP_MAPPING``, ``INSTRUMENT_ID_TO_MISSION_ID``, ``STAR_RA_DEC``, ``UNIT_FORMAT_DB``, ``MAX_DOWNLOAD_SIZE``/``MAX_CUM_DOWNLOAD_SIZE``, ``MYSQL_TABLE_NOT_EXISTS`` and 37 others.

The root cause is measurable and is in the *source*, not the prose: **130 of the 138 module-level constants under `src/` carry neither an attribute docstring nor a `#:` doc comment**, and autodoc emits no entry for such a constant even under `:undoc-members:` — so no `py:data` target is created. Spot-checking 17 named constants against the built HTML, exactly three had a target: `DATABASE_BRANDS`, `PDSTABLE_REPLACEMENTS` and `CACHE_TABLE_COLUMN_DEFS` — and those three are precisely the ones the guides already role correctly (`dev_guide_import_config.rst:471`, `:432`, `dev_guide_webapp_tools.rst:407`). The correlation is exact. What looks like an inconsistent house style is the authors correctly using a role wherever one would resolve.

The fix therefore runs source-first: give the constants that the guides name an attribute docstring (`src/opus_import/instruments.py:17-18` shows the pattern already in use — a `"""..."""` line under the assignment) or a `#:` comment, which creates the target *and* documents the constant in the reference; then role the 78 mentions. That is a worthwhile change on its own terms — `BUNDLE_INFO` is the registry the whole import pipeline turns on and it currently appears nowhere in the published reference.

**53 mentions of private helpers** (41 distinct: 24 in `dev_guide_import_obs.rst`, 14 in `dev_guide_webapp_results.rst`, 9 in `dev_guide_import_db.rst`, 3 in `dev_guide_import_config.rst`, 2 in `dev_guide_webapp_search.rst`, 1 in `dev_guide_import_obs_classes.rst`) — ``_get_download_info``, ``_api_get_images``, ``_valid_regex``, ``_time_from_index`` and the rest. `docs/_ext/opus_api_reference.py:144-153` emits `:members:` and `:undoc-members:` but not `:private-members:`, so none of them is in the reference. Three options, and this needs a decision rather than an edit: add `:private-members:` to the generator (weigh against F2.1, which argues for a *smaller* reference); record a scoped deviation in `docs/dev_guide_conventions.rst`; or rewrite those passages to describe the behavior without naming the helper.

**5 generated-model classes** (`Partables`, `TableNames`, `UserSearches`×2 at `dev_guide_webapp_search.rst:338,368`; `ObsPds` at `dev_guide_webapp_tools.rst:419`), from `opus_app.apps.search.models`, which `EXCLUDED_MODULES` deliberately keeps out of the reference — correctly, so these stay literals.

**6 third-party dotted names** with no Sphinx inventory (`django.setup()`, `Pds4File.use_shelves_only()`, `pdslogger.PdsLogger`, `markupsafe.Markup`, `settings.configure()`, `cache.clear()`) — likewise correct as literals, though `django.setup()` and `settings.configure()` would resolve if Django's inventory were reachable for them.

**F3.4 — Low. Narrative `:doc:` targets are coupled to generated page names, and that coupling is undocumented.**

14 of the 15 distinct `:doc:` targets (`api_reference`, `api_opus_*`) name pages that are **machine-generated and git-ignored** (`.gitignore:51-52`) — they do not exist in a fresh checkout. Nothing is broken: `opus_api_reference.setup()` calls `write_api_reference(app.srcdir)` at extension-load time, before Sphinx reads any source, so the pages are always present at build time. But the page names are derived from `PACKAGES` and `walk_package()`, so renaming a subpackage silently invalidates every hand-written `:doc:` target such as `dev_guide_webapp_results.rst`'s `:doc:`api_opus_app.apps.metadata``. The `-W` build is the only thing that catches it — adequate, but it is a real coupling between narrative prose and generated page names, and it is written down nowhere.

## 5. User guide

### Findings

**F5.1 — High. There is no user guide.**
`doc_user_guide.mdc` §1 requires the user manual to live in a dedicated `docs/user_guide/` subdirectory with a landing page and `user_guide_<topic>.rst` chapters. The `docs/` tree contains `dev_guide*.rst` (30 chapters), `api_guide*.rst` (3 chapters), the generated `api_reference`, and `code_of_conduct.md`. There is no `user_guide/` directory and no user-guide chapter.

The API guide is not a substitute. It is a manual for *callers of a deployed OPUS server's HTTP API* — `docs/api_guide.rst:6-12` says so — and it covers none of `doc_user_guide.mdc` §2's required content: no supported Python versions, no install command, no prerequisites, no environment variables, no expected input/output layout, no configuration model with precedence and defaults, no importable-API usage.

All of that material exists and is good. It is filed under the *developer* guide: `docs/dev_guide_installation.rst` (bringing up a server from a PyPI install), `docs/dev_guide_environment.rst` (prerequisites, `OPUS_CONFIG`, the environment-variable table), `docs/dev_guide_import_config.rst` (the configuration model), `docs/dev_guide_import_running.rst` (the complete `opus_import` CLI reference), `docs/dev_guide_web_server.rst`, `docs/dev_guide_deployment.rst`. But `docs/dev_guide.rst:6` addresses that guide to *"people who modify, extend, build, test, release or deploy OPUS"* — so a person who runs `pip install rms-opus` to use the import pipeline has no manual written for them and must read a contributor guide to find their own installation instructions.

Two mitigating facts, and they are real. First, the README (`:28-30`) states a deliberately narrow audience: published so the Node can deploy it and so the software is inspectable, with no API stability guarantees. Second, the project has clearly noticed — `docs/dev_guide_conventions.rst:27-28` lists `doc_user_guide.mdc` and `doc_how_to.mdc` together as *"The other documentation kinds, **for reference**"*, which reads as an acknowledgment that neither is being applied.

That acknowledgment is not, however, written anywhere a reader of the documentation can see, and the rule is not waived in the "Deviations" section of `docs/dev_guide_conventions.rst:68-79`, which records exactly one waiver (public web API back-compat). Two honest resolutions:
1. Create `docs/user_guide/` and re-home the user-facing chapters into it — installation from PyPI, configuration, and a per-program CLI reference for each of the three console scripts — leaving the developer guide to contributors. This is mostly *moving* existing prose, not writing new prose, for `opus_import`.
2. Or record the merge as a second deviation in `docs/dev_guide_conventions.rst`, stating that OPUS's users are API callers and its operators are its developers, so the user-guide rule is met by the API guide plus the deployment chapters. That is a defensible position; it is just not currently written down.

**F5.2 — High. The two log-analyzer programs' command-line surface is almost entirely undocumented.**
`doc_user_guide.mdc` §3 requires, for each shipped program, every option documented with its flag, argument, effect, default and any config equivalent, grouped by purpose, plus a synopsis and at least one runnable example. Measured by comparing each `argparse` parser against every mention in `docs/` and `README.md`:

| `opus_log_analyzer` (`src/opus_log_analyzer/log_analyzer.py`) | 21 optional + 1 positional = **22** | 8 optional | **13 optional + the positional** |
| `opus_error_analyzer` (`src/opus_log_analyzer/error_analyzer.py`) | 6 optional + 1 positional = **7** | **0** | **7** |

**F5.3 — Medium. The API guide documents one download format; the route serves three.**
`docs/api_guide_calls.rst:438` titles the section `api/download/[opusid].zip` and `:442` states *"Supported return formats: ``zip``."* The route accepts all three: `re_path(r'^api/download/(?P<opus_id>[-\w]+).(?P<fmt>zip|tar|tgz)$', ...)` at `src/opus_app/apps/cart/urls.py:22`. **F5.4 — Medium. An undocumented public query parameter on `api/download`.**

**F5.5 — Medium. An undocumented public API route.**

**F5.6 — Low. `--cronjob` is documented as current and deprecated at the same time.**
`docs/dev_guide_deployment.rst:232` and all three `scripts/server/log_analyzer/*.sh_template` files invoke `opus_log_analyzer --cronjob`, while the parser's own help text for that flag reads *"Deprecated. Use --batch instead"* (`src/opus_log_analyzer/log_analyzer.py:98`). Separately, `opus_error_analyzer`'s `--cronjob` (`src/opus_log_analyzer/error_analyzer.py:431`) is parsed to `dest='cronjob'` and **never read** — `expand_globs_and_dates(args, error_analysis=True)` runs unconditionally at `:450` — yet `--output`'s help at `:422` still says *"For --cronjob, specifies the output pattern"*, as though the flag gated something.

**F5.7 — Low. No synopsis or complete example for either log-analyzer program.**
`docs/dev_guide_log_analyzer.rst` names the console scripts and module forms (`:11-18`) but gives no invocation syntax block and no complete runnable command; its only command line is the elliptical `opus_log_analyzer --configuration myproject.configuration ...` (`:56`). ### What is strong
