# The mini-holdings fixture

A holdings-free test suite for the import pipeline: real subsetted metadata, shelf files for both PDS regimes, the production-default invocation, and goldens for every table — written to be executed by a fresh agent with no context beyond this page and the repositories.

2026-08-28 · final — hardened by four independent opus execution reviews (53 findings total, all resolved here) rms-opus @ `e4fe546e` · pdsfile rewrite @ /seti/all_repos/rms-pdsfile

**The design in one paragraph.** The import is index-driven: everything it computes comes from the index and metadata summary tables, and it never reads a data file's contents. So the fixture checks in **real, subsetted index and metadata files** — rows sampled for field diversity, not taken from the top — and **shelf files for both PDS regimes, as reviewable text manifests** carrying real checksums, sizes, image dimensions, and row keys. Production holdings have no PDS4 shelves yet, so the recorder _creates_ them with pdsfile's own maintenance tools and subsets the result, exactly as it subsets the existing PDS3 shelves. The build step only pickles manifests into a temporary holdings tree — **no stub files of any kind, ever**. The tests run the real `opus_import` CLI in production-default shelf mode; the one line of OPUS code enabled is `Pds4File.use_shelves_only()`, which runs under the pdsfile rewrite everywhere **by standing decision** (F13); §9's rewrite-install rule is what makes that decision true in every environment, the self-hosted workflow and the published wheel's floor included — the rewrite's filesystem fallback (F9) is why the rule admits no exceptions. The integrity guarantee is **not** a mode flag: it is the expected-products assertion (§5) — every recorded product must appear in `obs_files` and vice versa — because a shelf missing one key fails _silently_ , not loudly (F6). The pdsfile rewrite is used for every pdsfile role.

## §1 · How the import consumes holdings — the facts the design is built on

Each fact was verified against the code or the live holdings; an independent reviewer re-checked every receipt. File:line references are rms-opus (`src/opus_import/…`) or the pdsfile rewrite source.

  1. The import is index-driven: one metadata dictionary per observation, merged from the primary index, the ring/sky/surface-geometry summaries, the inventory, **and the supplemental index** , cross-referenced **by primary filespec**. The metadata directory is discovered by listing (`childnames`) and filtered on five conditions — basename starts with the bundle id, contains no `999` (cumulative files), and ends in one of `*SUMMARY.LBL`, `*SUPPLEMENTAL_INDEX.LBL`, `*INVENTORY.LBL` — then read through pdstable; the inventory CSV is read with plain `open()`. Supplemental columns are not marginal: seventeen obs classes read them, EBROCC among the heaviest. do_import_index.py:1–8, 203–238 (filter at 216–222) The metadata files are the fixture's real content, the filespec is the recorder's subsetting key, and the three filter patterns are §2's file-selection rule.
  2. The PDS3 index _label_ is load-bearing twice: pdstable needs it to parse the table, and it returns a label dictionary field functions read directly (`STAR_NAME`, `TARGET_NAME` in the EBROCC class). PDS4 index files carry no label — the CSV is read, columns typed by inference. safe_pdstable_read; obs_base.py:463–488; obs_volume_ebrocc_xxxx.py:108–132 Labels ship whole, with only `ROWS`/`FILE_RECORDS` edited.
  3. `opus_import` never opens a data file or reads its size: zero hits for `getsize`, `os.stat`, or binary `open`. verified by grep No data file needs to exist at all — shelves answer for every one.
  4. An observation's product set comes from `opus_products()`: per-volume rules generate candidates, existence filtering decides survivors, and candidates can cross PDS versions. Which candidates exist is **recorded reality, not derivable**. _opus.py:164, 274, 313 The recorder captures the expected-products set once from real holdings; §5's expected-products assertion then holds the import to it.
  5. Every `obs_files` row takes `checksum`, `size_bytes`, `width`, `height` from the info-shelf five-tuple (bytes, child count, modtime, MD5, shape). A width recorded as `'TBD'` makes pdsfile open the image with PIL, so manifests always carry measured dimensions. do_import_index.py:815–818; _properties.py:1021, 1041 Manifests subsetted from real shelves put real values in the database for free.
  6. **Shelf gaps fail in three different ways, and only one is loud.** A shelf _file_ that is missing: `shelf_exists_if_expected()` swallows the OSError and the product is skipped with a warning, regardless of `SHELVES_REQUIRED`. A _key_ missing from a present shelf: `os_path_exists` returns a silent `False` with no fallback and no warning — the candidate simply never existed. Only a property read on an already-accepted product raises under `SHELVES_REQUIRED`. _shelves.py:606–626; do_import_index.py:802–813; _local_fs.py:179–181; _properties.py:823 An under-provisioned manifest therefore produces a quietly smaller import that regeneration would bless. No mode flag prevents this; the expected-products assertion in §5 is the guard, and it is the single most load-bearing test in the suite.
  7. For each PDS3 index-type product, `find_selected_row_key()` checks the observation is present in the `_indexshelf-metadata` row files; a missing lookup skips the product. The check is gated `pds_version == 3` — **PDS4 index products are deliberately assumed present and never consult an index shelf**. do_import_index.py:763–776 PDS3 index-shelf manifests are checked in, built over the subsetted tables so row keys match by construction. PDS4 index-shelf manifests are NOT checked in — they would be dead content until that gate is widened, which is out of scope here.
  8. A label product whose link-shelf entry is missing keeps importing but loses its `.fmt` companions, with a warning. _opus.py:341–347 Link-shelf manifests are included for every (category, bundle) the expected-products set touches.
  9. The import leaves `Pds4File.use_shelves_only()` / `require_shelves(True)` commented out. This design enables **the first line only** : with `SHELVES_ONLY` on and no `require`, a missing shelf is caught in `os_path_exists` and falls to the filesystem, `os_listdir` answers from the real tree when the shelf tree has no matching directory, and `glob_glob`'s contract is “if no shelf file covers the pattern, the filesystem glob answers after all.” cli.py:559–565; _local_fs.py:176–191 and the os_listdir / glob_glob docstrings One enabled line gives the fixture shelf-answered PDS4 existence — zero stubs. **The fallback exists only in the rewrite** : 0.0.18's empty-key branch is `else: return False` with no fall-through (installed `pdsfile.py:1341–1349`), and enabling the line there breaks every PDS4 existence check — verified empirically, `from_path` raises `UnboundLocalError`. The line is safe exactly where the rewrite is installed, which §9's rewrite-install rule must make everywhere the import runs, the self-hosted integration workflow included.
  10. The four PDS4 shelf builders ship as maintenance tools (`pds4checksums`, `pds4infoshelf`, `pds4indexshelf`, `pds4linkshelf`), and `pds4infoshelf` **reads digests from the checksum file rather than computing them** — a hard dependency, so `pds4checksums` runs first. holdings_maintenance/pds4/{pds4checksums,pds4infoshelf,pds4indexshelf,pds4linkshelf}.py; pds4infoshelf.py docstring The recorder's PDS4 sequence is fixed: checksums, then info/link shelves, in a staged scratch tree.
  11. Preload reads `_volinfo` with **raw** `os.listdir` (must physically exist; Pds4File skips it by class-name check; icons optional). Category detection uses the _shelf-backed_ existence calls, so `volumes/`, `previews/` and the other category directories need not exist on disk — the `_infoshelf-*` trees stand in for them. That substitution string-replaces the holdings directory's literal name, so the built roots must be named exactly `holdings` and `pds4-holdings`. _preload.py:399–411, 764–779; _local_fs.py:277; pds3file:126; pds4file:118 The built tree is minimal: metadata, `_volinfo`, the shelf trees — plus the in-volume `INDEX/` directory for the bundle types whose `primary_index` is not under `metadata/` (e.g. COCIRS_5xxx's `OBSINDEX.LBL`): `do_import.py:123–133` probes _every_ primary-index search path — the metadata directories included — with **raw** `os.path.exists`/`os.listdir`, so each bundle's metadata directory and primary index must physically exist in both regimes (§2 satisfies this), and the in-volume `INDEX/` files are materialised under `holdings/volumes/…`.
  12. Shelf paths are `<root>/_<type>shelf-<category>/<bundleset>/<bundle>…​.pickle` — confirming `_infoshelf-bundles` etc. for PDS4 by construction — and index shelves are **per index table** : production carries four pickles for COISS_2111. _shelves.py:205–243; verified against holdings Manifest granularity mirrors the pickles one-to-one.
  13. The pdsfile **rewrite** is used for every pdsfile role — the import under test, the recorder, and the tools. The 0.0.18 wheel never runs against the fixture. Every pdsfile receipt in this document was read from the rewrite, so the verified behavior is the behavior the suite gets. The rewrite ships `py.typed` and stubs, with consequences §9 assigns. rfrench decision, 2026-08-28
  14. The bundle registry is `config_bundle_info.BUNDLE_INFO`, a **list of (regex, info) tuples** — each entry's regex matches bundle ids, **one entry may span several volsets** (one covers both COISS volsets), and some entries carry `instrument_class: None`, deliberately ignored. Per the standing no-hand-counts rule the entry totals are not written here; iterate the list to regenerate them. One registered class, `cassini_iss_fring_mosaics_rsfrench2025`, has **no bundle in the holdings tree** and its line in `scripts/import/import_for_tests.sh:37` is commented out. config_bundle_info.py:94; verified against pds4-holdings The volume set enumerates from this registry, not from a filename glob — a glob over `obs_volume_*.py` counts shared base classes that own no bundle and misses the PDS4 `obs_bundle_*` classes entirely.
  15. Current holdings-free coverage of `opus_import`: **39%** overall; `steps/` 13% with the pipeline core near zero (`do_import_index` 3%, `do_import` 4%, `do_validate` 4%, `do_import_obs` 6%, `do_import_tables` 7%); `importdb/` 26%; `obs/` 51% but largely import-and-introspect (~12,000 lines) — branch coverage, as the repo configures it. pytest --cov, measured 2026-08-28 The prize is the pipeline core executing end-to-end and the obs layer executing against data.

### 2.1 · File formats — the contracts, with one example each

  * **Shelf manifest (`.pydict`)**: the file is a single Python dict literal — no assignment, no imports — loaded with `ast.literal_eval()`. The extension is deliberately not `.py`: manifests are data, and `.pydict` keeps them out of ruff-format, mypy, and vulture entirely. Filename rule: `<type>shelf-<category>.<bundleset>.<bundle>[.<table>].pydict` maps to `<root>/_<type>shelf-<category>/<bundleset>/<bundle>_<suffix>.pickle` (index shelves: `…/<bundleset>/<bundle>/<table>.pickle`), where suffix is `info`/`links` per F12. Values are exactly the shelf's own tuples, modtimes in the shelves' native `'2018-05-04 11:07:16.000000'` form — pdsfile parses them by fixed character offsets, so an ISO-`T` form raises — e.g. `{'': (5582286, 10, '2018-05-04 11:07:16.000000', '', (0, 0)), 'COISS_2111_index.lbl': (8944, 0, '2018-05-04 11:07:16.000000', 'd41d…', (0, 0))}`. The recorder copies real values, so the format is right by construction; this note exists so nobody "normalises" it. **Layout is pinned for diffability** (ruled 2026-08-30): one entry per line — the key and its whole value tuple on that line — keys sorted lexicographically, opening `{` and closing `}` on their own lines, so a recorder re-run's diff shows exactly the entries that changed and nothing else. Never a one-line dict, never `pprint`'s width-driven wrapping, which splits tuples across lines and turns one changed value into a multi-line diff.
  * **Expected products (`expected_products/<bundle>.tsv`)**: one line per product file: `<root-relative path>\t<bytes>`, where the path starts with `holdings/` or `pds4-holdings/` — a cross-PDS product (F4) would appear in a PDS3 bundle's expected-products file with a `pds4-holdings/` prefix — the rule for when such a target bundle lands in the holdings; today none is present, so no expected-products file contains one. Sorted; the drift report is its diff, and §5 asserts against it.
  * **Golden (`goldens/<table>.tsv`)**: header row of column names, then rows ordered by primary key, values as MySQL returns them — **except every column whose packaged schema declares`"field_type": "timestamp"`, which the serializer drops entirely**: `importdb/mysql.py` renders those as `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` and `do_import_obs.py` never writes them ("Always skip 'timestamp' fields"), so they are wall-clock by construction in every goldened table. No other column is normalized: from an empty database the import is deterministic (ids assigned in table order from `find_max_table_id`), and **any non-timestamp column that differs between two consecutive clean runs is a bug, not a normalization candidate**.
  * **Warning whitelist (`warning_whitelist.txt`)**: one regex per line, `fullmatch`-ed against the complete warning message; `#` lines are comments and every entry carries one saying why it is benign. **An entry that matches no warning in the run fails the suite** — a stale whitelist is itself a defect. The file's diff history is the record of every warning ever accepted. The match target is the message _after_ pdslogger's timestamp/level/name prefix is stripped — regexes match content, not clock. Non-empty on day one and likely substantial: beyond the sequence's own `** DELETING ALL PERMANENT TABLES **` and `Importing on top of previous import tables!`, the seed is **the first recorded run's own WARNINGS.log** — each distinct message reviewed, given its why-benign comment, and admitted one at a time. `scripts/import/find_unknown_warnings.sh` is explicitly **not** a source: it is an old file that has not been kept up to date, and seeding from it would launder stale patterns into a file whose entire value is that every entry was justified against a real observed warning (ruled 2026-08-30).
  * **Exclusions (`exclusions.tsv`)**: `<instrument_class>\t<reason>` — today one line, `cassini_iss_fring_mosaics_rsfrench2025`, whose bundle is absent from the holdings (F14).

## §3 · The recorder

One deterministic script, run on the holdings machine; its re-run diff against the checked-in fixture is the drift report.

  * **Enumerate the volumes** : the set is one representative volume per **volume type** — per entry of `config_bundle_info.BUNDLE_INFO` (F14), one entry per bundle-id pattern, which may span several volsets (F14) — **avoiding every volume`scripts/import/import_for_tests.sh` names** — the self-hosted integration run already imports those, so a disjoint fixture buys coverage CI does not otherwise have (ruled 2026-08-29). The deterministic choice: sort the bundles the entry's regex matches in the holdings, drop the ones the script names, and take the **middle of what remains** (0-based index `⌊n/2⌋`) — not the first: a volset's early volumes are typically the boring start of a mission, pre-encounter, before the instrument hits anything interesting, so a first-volume rule systematically picks the worst representative (ruled 2026-08-29). No new volumes will ever be added to current volsets, so the pick is stable across recorder runs. Where the type offers no choice (the regex matches exactly one bundle — EBROCC_0001, the single-bundle `VG_28xx` entries, and their like), the overlap with the script is unavoidable and accepted. A candidate that fails the fixture's own gates (unwhitelistable import errors, a failing expected-products check) is skipped in favour of the next index in sorted order, wrapping to the start, and each skip is recorded with its reason in the recorder's notes — so the recorder is reproducible in every case. A second volume from the same volset is added **only when its index files carry fundamentally different values** ; to make that a check rather than a memory, the recorder compares column sets and per-column value profiles across each volset's volumes and reports any volume whose index schema differs from the chosen representative's, so the addition is a reviewed decision, not a discovery. A type with no bundle in the holdings goes into `exclusions.tsv` with its reason; the completeness check compares registry minus exclusions against the fixture, so a newly registered type fails the recorder rather than silently missing coverage. Every representative is sampled to class coverage under one budget rule (§6).
  * **Select rows by diversity, not position — and diversity means code paths, not magnitudes** (ruled 2026-08-30): parse the index and summaries with pdstable, then greedy max-coverage — seed one row, repeatedly add the row introducing the most unseen (column, _class_) pairs, where a value's class is whatever would send the import down a different branch. The classes: for categorical columns, each distinct value (these become the mult choices); for every column, _missing / N/A / None / the column's sentinel value_ is a class of its own, distinct from a-real-value-is-present; for paired range columns such as longitudes, _wrapped (min > max) versus unwrapped_; and every numeric value that is none of the above collapses into a single present class — an exposure of 0.1 s and one of 100 s execute exactly the same code, so numeric spread buys nothing and is not scored. Guarantee every distinct target and mult value _observed in the volume's own index_ , up to the budget — a single volume cannot carry mult values that occur only elsewhere in the archive, and the guarantee does not pretend otherwise (ruled 2026-08-30). The budget is class-driven for every volume alike — no tiers: keep adding rows until every observed (column, class) pair is covered, floor 2, cap N≈20 (§6, ruled 2026-08-30). Seeded and deterministic.
  * **Extract the selected rows** from each fixed-record table (fixed-length records concatenate), pull the matching summary and inventory rows by primary filespec (F1), rewrite `ROWS`/`FILE_RECORDS`. For a bundle type whose `primary_index` lives inside the volume rather than under `metadata/`, subset that in-volume index the same way into `pds3/volume_index/…` (§2) — the import reads it off the real filesystem (F11).
  * **Record the expected products** : with shelves loaded, run `opus_products()` per selected observation; write every returned path and size — mathematically the closure of the sampled observations under `opus_products()`, but the directory is named for what the tests do with it: `expected_products/` (renamed from `closure/`, ruled 2026-08-30). Two path families are dropped, by decision: documents-tree paths, and **every path under a versioned volset** , matched as a bundleset name ending `_v\d+(\.\d+)*` — the holdings carry single-digit forms (`calibrated/COISS_2xxx_v2`, `GO_0xxx_v4`) alongside `_v1.0`-style ones, and a pattern that missed `_v2` would quietly ship a versioned tree with no test going red. The fixture contains no versioned trees, so the import produces no versioned `obs_files` rows and the §5 expected-products assertion stays bidirectional by construction; the version-handling branch runs but only ever sees "Current" (§7).
  * **Obtain shelves, per regime, in a staged scratch tree — never writing into production holdings** : PDS3 shelves are read from production; PDS4 shelves are built in the scratch tree with the tools in checksum-first order (F10), for _every_ PDS4 bundle any expected-products file touches, then read. The staging mechanism is named, not improvised: the scratch `pds4-holdings/` holds a **plain copy** of each needed bundle — never hard links or symlinks: the recorder must run on Windows, and the scratch tree may sit on a different filesystem from the holdings; the files involved are small enough that copying is the whole answer (ruled 2026-08-29) — so the tools read real bytes and write shelves only into scratch — with `TZ=UTC` pinned first (shelf modtimes are formatted in the local time zone, per `pds4infoshelf`'s own docstring — unpinned, the drift diff goes noisy across machines and DST) and the tools' log root (`PDS_LOG_ROOT`/`--log`) pointed into scratch, so nothing they write lands outside it. Index shelves for both regimes are built by `pdsindexshelf`/`pds4indexshelf` over the already-subsetted metadata staged into the scratch tree — but only PDS3's become manifests (F7).
  * **Emit manifests** : filter info- and link-shelf dicts to the expected-products keys plus every ancestor directory entry, then enforce one invariant: _the metadata info-shelf manifest contains an entry for every file physically checked in under that bundle's metadata directory, in the expected-products set or not_ — asserted by the recorder, because summary discovery lists that directory from the shelf (F1) and a missing entry silently loses a summary. Write them in §2.1's pinned layout — one sorted key per line, the value tuple on the same line — and run the emitted files through an `ast.literal_eval` round-trip before writing, which also proves the formatting never altered the data.

## §4 · The build step and the exact run

  * A session-scoped conftest fixture assembles a temp tree with roots named exactly `holdings/` and `pds4-holdings/` (F11): copies the real content files, pickles every manifest to the path its filename encodes (§2.1). No maintenance tools, no network, no stubs — and **no`.py` shelf sidecars**: pdsfile has a null-key fast path that reads a sidecar, but the import never reaches it, and production holdings carry no sidecars either, so pickles alone are sufficient by the same evidence production runs on.
  * Writes the run's `opus.toml` — **every key`opus_config`'s validator requires**, not just the interesting ones: holdings paths at the temp tree, root database credentials from the environment (§9's workflow row), the run's PID-keyed schema name (next bullet), per-run `import_log_dir` and log-file paths, and a throwaway Django secret — and exports `OPUS_CONFIG` pointing at it.
  * **Schema names, and their teardown, are pinned here** (ruled 2026-08-30): the main run imports into `opus_import_test_<pid>` and each §5 negative case into `opus_import_test_<pid>_<case>` (`_dupid`, `_ignore_errors`), where `<pid>` is the pytest session's own PID — not a username or matrix-leg label, because the collision that matters is one developer running two worktrees against the same MySQL server at once, and the PID is unique per concurrently live run where a username or branch name is not. `build_run.py` records every schema it creates, and the session fixture's finalizer `DROP DATABASE`s them all on the way out, **pass or fail** — a failed run's evidence is its logs and its goldens diff, never a parked schema. A run killed too hard for the finalizer leaves its schema behind; the PID naming keeps such a stray from ever colliding with a later run, and anything matching the `opus_import_test_` prefix is safe to drop by hand.
  * **The exact invocation** , in the order `scripts/import/import_for_tests.sh` actually runs: `python -m opus_import --drop-permanent-tables --scorched-earth`, then **one`--do-all-import` invocation per bundle** (the script's own shape — it is what produces the on-top-of-previous-import warnings §2.1 expects, and it fixes the id-assignment order the goldens encode; bundles in registry order — `BUNDLE_INFO` entry order, lexicographic within an entry — a fixed order because the goldens encode it; the script's own volume list is no guide, since the fixture deliberately avoids its volumes). The script's one extra flag, `--import-check-duplicate-id` on its GO line, is **not** carried on the main run — it belongs to the §5 negative case. Then `--cleanup-aux-tables`, then `--import-dictionary` (the packaged `pdsdd.full` — deterministic, shipped in the wheel; the plan's earlier "trimmed pdsdd" idea is superseded by using the real one), then `manage.py migrate` (Django contrib tables; excluded from goldens), then `--validate-perm`. **No shelf-mode flags** — in particular, neither `--dont-use-shelves-only` nor `--import-dont-use-row-files`: PDS3 runs shelves-only with shelves required, PDS4 runs the newly enabled shelves-only-with-fallback (F9).
  * **Subprocess, with coverage plumbing** : the CLI runs as a real subprocess — identical to production, and immune to pdsfile's class-level global state and the repo's `filterwarnings = ["error"]`. Coverage crosses the process boundary via `COVERAGE_PROCESS_START` plus a `coverage.process_startup()` `.pth` hook installed by the builder into the venv; `[tool.coverage.run] parallel = true` is already set, which is the other half.

## §5 · What the tests assert

  * **The expected-products assertion — the load-bearing one (F6):** every path in every bundle's expected-products file appears as an `obs_files` row, and every `obs_files` row appears in an expected-products file. A shelf-manifest gap makes a product silently vanish with no error and no warning; this bidirectional check is the only thing that turns that into a red test. Comparison rule: expected-products paths are root-prefixed (`holdings/…`, `pds4-holdings/…`) while `obs_files` stores logical paths, so the assertion prepends each row's regime root before comparing. The expected-products files exist to be asserted against, not merely diffed.
  * **ERRORS.log empty** — the import's real gate is the log, not the exit status.
  * **Zero unexpected warnings** against `warning_whitelist.txt` (§2.1), and zero stale whitelist entries.
  * **Golden rows for every table the run leaves behind** , discovered by §5.1's rule, never by a list here — the exclusion is exactly the tables `manage.py migrate` creates, so `cart` (created by `--cleanup-aux-tables`) and even `django_session`, which has a packaged OPUS schema, are goldened whenever the run creates them. Written only by `make_mini_goldens.py`, never by hand or by a test run.
  * **Re-import — the upsert-update path** : after the golden comparison passes, run `--do-all-import` once more for **a single volume, the COISS representative (§6)** , and compare against the goldens again under the same timestamp-column exclusion (§2.1). Execution disproved this bullet's original claim that nothing but timestamps changes: ids are assigned from `max()` over both id namespaces and the perm-table delete runs afterwards, so the re-imported bundle's rows are renumbered by design. The assertion as executed is split in three: tables without the re-imported bundle are byte-identical (exactly the mult tables, where the upsert-update lands), tables with it hold the same rows modulo the surrogate id columns, and neither half may be empty. This is not a determinism proof — the import is deterministic by design and that is not in doubt (ruled 2026-08-30) — it exists because a second import of the same observations is the only thing in the suite that executes the _update_ half of every upsert: the documented re-import operational mode, and exactly where the `AS new` row alias lives. One volume buys that coverage at a fraction of a full second pass.
  * **Every`obs/` function proven executed — coverage by actual execution, not introspection** (ruled 2026-08-30): after the run, parse the `coverage.json` the Import Tests job already produces and read the per-function region of every function and method under `src/opus_import/obs/`. Coverage.py attributes a function's `def` line to the enclosing module region, so a method that was merely imported — or enumerated by introspection but never called — reports 0% in its own region; only a real call registers (verified empirically against coverage 7.13; function regions in the JSON report arrived in `coverage 7.6.0` — not 7.5 as this document first claimed, corrected from the sdists during execution — so the dev-extra floor moves from `>=7.0` to `>=7.6`, §9). Every function must show at least one executed line, except entries in a checked-in whitelist, `import_tests/fixtures/unexecuted_methods.txt`, each carrying a comment saying why the fixture cannot reach it (a field of a table no sampled volume populates); an entry naming a function that _did_ execute, or that no longer exists, fails the suite. This check is §3's sampling rule made measurable: an unexecuted method is exactly a branch the sampled rows never reached, so its report is also the recorder's guide to where sampling is thin. It costs nothing at runtime — it reads a file the job already writes.
  * **Negative cases** : missing-summary branches via the set's naturally metadata-less volumes; a crafted duplicate-opus-id pair for `--import-check-duplicate-id`; an `--import-ignore-errors` run pinning #1478's behavior. The crafted inputs live in `import_tests/fixtures/negative/` — **hand-authored, owned by the tests, never touched by the recorder** — and the ignore-errors case perturbs an unknown `TARGET_NAME` in a copied index row, the documented `'OTHER'`-fallback path. Execution model: `build_run.py` is parameterized by fixture-tree overlay, schema suffix, and log directory; each negative case is its own run into its own schema with its own logs (pdslogger appends, so a shared log directory would pollute the main run's assertions), asserting on _its_ ERRORS/WARNINGS and exempt from the main run's clean-log rules.
  * **Unit layers** (claimed from the plan's PR-19 section, §10): direct tests for `import_util`, `config_targets`, and `importdb.mysql` alongside the end-to-end run.

### 5.1 · How the goldens are actually checked

One shared serializer module, `import_tests/tools/golden_io.py`, is the only code on either side of the comparison — `make_mini_goldens.py` calls it to _write_ and the tests call it to _read and compare_ , so the two sides agree on the format by construction rather than by convention. It reads the database directly over MySQLdb (the same driver the import uses), with the credentials and schema name from the run's generated `opus.toml`:

  * **Table discovery is a rule, not a list** : `SHOW TABLES`, minus exactly the set `manage.py migrate` creates — captured by the builder as the before/after diff of `SHOW TABLES` around the migrate step — so a table the import newly writes appears as a golden-missing failure instead of silently escaping comparison, and a table it stops writing fails as an orphaned golden.
  * **Row order** : `SELECT *` ordered by the table's primary key, read from `information_schema` — never by insertion order.
  * **Serialization** : values as MySQLdb returns them, rendered to the §2.1 TSV form; NULL spelled distinctly from empty string.
  * **Comparison** : byte equality per table file; on mismatch the test emits a unified diff of golden versus actual, so a failure reads as rows, not as a boolean.

## §6 · Volumes: one set, every type sampled to class coverage

**There is no breadth/depth split** (ruled 2026-08-30, superseding the two-tier design): every volume type gets both — breadth from being in the set at all, depth from the class-driven budget. The set is one representative volume per **volume type** — per `BUNDLE_INFO` entry with a non-`None` `instrument_class` (an entry may span several volsets — F14), minus `exclusions.tsv` — chosen by §3's selection rule. Every representative is sampled identically: the sampler adds rows until every observed (column, class) pair in its index is covered — every mult value, every missing/sentinel contrast, every wraparound case — with a floor of 2 and a cap of N≈20. Metadata-less volumes arrive here naturally. Rows are the cheap part of the fixture — labels and shelf manifests are per-volume and do not grow with row count — so exploring every volset's branches costs almost nothing beyond what one volume per type already costs.

Three types carry named rationales — _not_ larger budgets — because they anchor structurally distinct pipelines the suite must be seen to exercise:

## §8 · Standing risks

  * **The fixture encodes pdsfile's current answers.** A pdsfile upgrade that changes `opus_products()` breaks the fixture in a way that looks like an OPUS bug. The recorder is the mitigation: regenerate, diff, review — don't debug.
  * **The fixture's PDS4 shelves lead production's.** When production builds its own PDS4 shelves, enabling the still-commented `require_shelves(True)` gives PDS4 the same guarantees as PDS3, with no fixture change. The planned real PDS4 index labels and summary metadata likewise slot in — the regimes share one structure on purpose.
  * **Manifest-format coupling.** The manifests mirror the shelf tuples; a pdsfile shelf-schema change moves the recorder and builder with it — one script each, both in this repo.
  * **Two regeneration programs, two deliberate acts.** The recorder (holdings machine) regenerates the fixture; `make_mini_goldens.py` (MySQL only) regenerates expected output. Neither runs in CI; both diffs are reviewed; nothing else may modify what they own; fixture regeneration precedes golden regeneration. The developer guide documents both procedures.

## §10 · What this supersedes, and the plan obligations it inherits

This document replaces the plan's **§4 PR-19 section** (not just the §2 layout line).   * **The codecov upload** : claimed — the new run's coverage joins the existing upload (§9).
